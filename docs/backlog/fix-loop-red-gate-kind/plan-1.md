## 2. Collect attributable test results on both trees

Work in `src/pipeline/gates.ts:31–45,106–198,227–262,343–429` and use the existing `RunResult` and `TestCase` contracts in `src/runners/types.ts:7–40`.

1. Add a fix-loop scoped runner path using `runSuites` and the existing pipeline runner options. Return the current `RunResult` directly and record it with `recordResults` in `tests.json` and `tests.log`. Run only the changed test paths and keep the established runner retry behavior. Use the result from that invocation to avoid stale reports after a launch or parser error.
2. Classify cases by the normalized project-relative path and full runner-visible name. Compare against the committed version of the file at the start of the fix cycle, including when a resumed attempt has uncommitted correction files. For existing changed files, use a targeted runner inventory of their pre-fix versions when identifying old cases. Reuse the detached worktree runner with the pre-fix commit’s test files and the current non-test changes overlaid, including uncommitted implementation from local mode. Carry over non-test additions, modifications and deletions so the old test files see the same implementation as the current run. This compares real names for generated and parameterized cases as well as literal titles. For a new test file there is no old inventory. Apply Decision 3 in the prompt and the gate: additions and changed assertions use fresh unique runner-visible names. A retained title supplies no evidence about a changed assertion. Reject duplicate identities that make candidate matching ambiguous, an unreadable prior inventory for a modified file, and an empty candidate set. Keep the title matching and diagnostics for initial Red tests intact.
3. For files containing passing candidates, reuse `withWorktreeAt` to overlay their current test files onto `origRedSha` and run them at that commit. Keep the baseline report separate from the current-tree result and log. Match each passing candidate by the same file and full name. Require an explicit named failure at the baseline per Decision 4. Treat a matching pass as vacuous. A skipped, missing or ambiguous match, an unavailable baseline, and a file-load error without a named result give insufficient evidence. An attributable current-tree failure needs no baseline run.
4. Surface runner and suite problems with the affected file or case and relevant output. A bare failing exit code, empty or missing report, skipped case, or suite-load error cannot supply a failing test for a blocker. Use the existing detached worktree cleanup for every exit path.

## 4. Continue the same Review fix cycle across process starts

Work in `src/pipeline/review-gate.ts:14–20,162–250` and `src/pipeline/run.ts:266–338`.

1. Update `findingsText` to give separate instructions by finding kind. Blocker tests exercise the real code and fail now for the stated reason, and the agent reports already-satisfied blockers as wrong findings. Missing-test cases pass now and fail as named cases at the original red commit. Include the fresh-title rule and keep implementation-only imports inside their cases. Carry the structured findings with the rendered prompt and preserve unrelated prompt values when restoring or clearing fix context.
2. Extend `ReviewRound` with an optional numeric loop ordinal and optional `acceptedFiles`. Derive the cumulative count from persisted ordinals, recognizing legacy `fix loop N of M` outcomes. Count each round once. A plain `changes requested`, a limit stop, or a passing round does not by itself consume one. Legacy `fixed` rows can have lost the information about whether a slot was used. Carry forward the highest surviving legacy ordinal as the recorded count, with no inferred increment for an ambiguous row. When a new Review round reports findings, enforce `review.maxLoops` before reserving a slot. Keep the existing `REVIEW NOT RESOLVED after <maxLoops> fix loop(s)` stop and its manual recovery commands. Store the new ordinal and loop outcome before entering the fix cycle. Preserve the ordinal when the outcome changes and use a separate per-process flag for intra-loop Review sync so historical loop counts do not cause a duplicate startup sync.
3. Have `fixCycle` and explicit Red tests resume use the same continuation after the Red tests result. For the skip, save `implement-skipped` and `acceptedFiles` on the originating round, then print `Implement skipped: no new test fails on the current tree; every accepted test covers a missing-test finding` once and go directly to Review. Preserve the skip outcome when the next Review reconciles the old findings. For a failing case, keep the existing `red.json` preparation, Implement sync, Implement and conditional Test repair. Keep the current-tree report available to Implement and remove the old blanket “wrong or already fixed” exception rewrite. Keep `decisions.md` reserved for Spec answers.
4. Add one startup restoration helper called in `stages` for an explicit `--from red-tests` start, after setup and before running the agent. Use only the latest changes round with open findings and a non-final outcome. Rebuild the exact `findingsText` from the in-process path. Ignore absent history, a passing or resolved round, `implement-skipped`, and a limit stop. Finish the restored round through the same continuation and then enter Review. Reuse the stored ordinal, and if history stopped at `changes requested` before a loop was reserved, apply the same limit check and reserve that round's slot once before proceeding. Keep ordinary starts at Red tests on the initial path.
5. On an explicit Spec or Plan restart, include `review-rounds.json` in the startup `setAside` call before either stage runs. A subsequent Review starts a fresh history. Full discard already removes the worktree and run record in `src/runs/index.ts:651–681`.
