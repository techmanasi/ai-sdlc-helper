# Detached supervisors already outlive server crashes

The web server does not host the coding agents. Each pipeline run starts under its own **detached supervisor process**: a new session and process group, no controlling terminal, and output written only to files. So when the `ai-sdlc-helper ui` server is SIGKILLed, crashes, gets Ctrl-C, or loses its terminal, **pipelines, agents and test runs keep going**. A restarted server finds them again from the file registry without any reattach step. That answers questions 1 to 3 better than the question assumed: the isolation exists. What is missing is safeguards around it. A supervisor killed on its own leaves a live pipeline and agent that the registry reports as stopped and that Stop cannot reach. PID reuse is not detected. And two server-side paths, dashboard triage sessions and the command palette, do run agents as direct children of the server and die or get orphaned with it. Test isolation (question 4) is weak: parallel runs share `node_modules`, `TMPDIR`, `HOME`, ports, databases and the CPU. But the only interference seen so far is CPU and process-start contention. Docker does not fix that, and on macOS it costs a 2.5 to 3x file I/O penalty on Docker Desktop. The best fixes for questions 5 and 6 are scheduling changes. A machine-wide budget for "test slots" should replace uncoordinated per-run workers, and the pipeline should stop repeating test work: a nominal run executes the **full suite four times plus three partial runs**, several of them on an unchanged tree.

## The server starts runs but never parents them

When the board starts a run, the server process calls `start()` directly. That function does synchronous git work under a file lock (`git worktree add`, copies, symlinks) and then spawns one supervisor with `detached: true`, stdio redirected to a `wrapper.log` file, and `unref()` ([src/runs/index.ts](../../src/runs/index.ts); [src/runs/supervisor.ts](../../src/runs/supervisor.ts)). Node documents this exact pattern for background work. On non-Windows systems a detached child becomes "the leader of a new process group and session", and it survives the parent only if its stdio is "not connected to the parent" ([Node.js child_process](https://nodejs.org/api/child_process.html)). Below the supervisor, nothing else is detached. The pipeline (`node dist/bin.js pipeline <slug>`), the `claude`/`codex`/`agy` agents, integration commands and test runs all inherit the supervisor's process group. Each one writes to its own log files (`run.out`, `<stage>.json`, `integration.log`), so none of them holds a pipe back to the server ([src/pipeline/agent.ts](../../src/pipeline/agent.ts); [src/pipeline/gates.ts](../../src/pipeline/gates.ts)). An experiment on this Mac confirmed the layout. The server's process group differed from the supervisor's, and the pipeline and the agent shared the supervisor's group.

There are two real exceptions, where the server does parent long-lived or agent processes. First, **dashboard triage sessions** spawn `claude` as a non-detached child with stdio on pipes ([web/server/triage.ts](../../web/server/triage.ts)). Second, the **command palette** (`POST /projects/:p/command`) runs any CLI arguments as a piped child with a 120-second timeout ([web/server/index.ts](../../web/server/index.ts)). Typing `pipeline <slug>` there starts a full pipeline, with its agents, under the server, with no supervisor and no run record, and SIGTERMs it after two minutes. That is a misuse path the UI does not block. Palette `run start <slug>` is safe, because the CLI child launches its own detached supervisor and exits.

## Server death spares pipelines, but four holes remain

The `ui` command handles only SIGINT and SIGTERM. Both lead to `server.close()`, which kills triage sessions but never touches pipeline runs ([src/cli/ui.ts](../../src/cli/ui.ts)). The startup banner says so: "Stop with Ctrl-C; runs go on without it." Two experiments with the real spawn options showed how each kind of child fares. When the server was SIGKILLed, the supervisor was reparented to PID 1 and kept running with its pipeline and agent. When the server's pseudo-terminal was closed, the server and its piped child died of SIGHUP, while the supervisor chain, which has no controlling terminal, survived.

| Child process | Server SIGKILL or crash | Ctrl-C | Terminal closed (SIGHUP) |
|---|---|---|---|
| Supervisor, pipeline, agents, tests | keep running | keep running | keep running |
| Triage `claude` session | orphaned, keeps editing, pipes broken | SIGINT from the tty plus SIGKILL from `close()` | SIGHUP kills it; run stays marked `running` until the next start |
| Palette command (including `pipeline`) | orphaned; a pipeline continues with no record | SIGINT aborts the agent | SIGHUP aborts it |

Reattaching works because the server keeps no in-memory run state. Every view re-reads `<git common dir>/sdlc-runs/<slug>.json`, which is written atomically (tmp file plus rename), and checks whether the supervisor PID is alive ([src/runs/records.ts](../../src/runs/records.ts)). Stop from a restarted server writes an interrupt marker, SIGTERMs the supervisor tree, and SIGKILLs after 10 seconds ([src/runs/index.ts](../../src/runs/index.ts)).

The holes sit one level down, and the worst one is a **supervisor killed alone** (SIGKILL, or the OOM killer). Its pipeline and agent are reparented to PID 1 but keep the dead supervisor's process group. `finish()` never runs, so the record stays `running` with a dead PID, which the board displays as `stopped`. Stop returns "not running". `killTree` cannot find the orphans, because its `ps` parent-PID walk starts from a PID that no longer exists. And `start()` passes its running check, so it can **launch a second pipeline into the same worktree** while the first one is still editing. A **pipeline killed alone** orphans its agent the same way: the AbortSignal never fires, and nothing sweeps the process group. **Test runs use `spawnSync`**, so the pipeline's signal handler cannot run until the suite returns ([src/runners/run.ts](../../src/runners/run.ts)). Last, `alive()` checks only that a PID exists and is not a zombie. A stale record whose PID the OS has reused therefore shows as running, blocks new starts, and would make Stop kill an unrelated process tree. No test covers killing the supervisor alone or the pipeline alone. The only kill test SIGKILLs the whole tree ([test/runs.test.ts](../../test/runs.test.ts)).

## Hardening the supervisor beats a daemon or service manager

The current design is the right base. A long-lived worker daemon would survive UI crashes, but it becomes a new single point of failure unless something else supervises it. CI runners use this listener/worker split, but they also keep one subprocess per job and coordinate through files ([actions/runner design](https://github.com/actions/runner/blob/main/docs/design/auth.md); [Buildkite agent configuration](https://buildkite.com/docs/agent/v3/configuration)). The supervisors already give ai-sdlc-helper both. PM2 restarts a process whenever it exits, which is the wrong model for a finite job, and it would add a heavy global dependency ([PM2](https://pm2.keymetrics.io/docs/usage/process-management/)). Durable-execution engines such as DBOS recover workflows from checkpoints in a database whose official backend is Postgres ([DBOS architecture](https://docs.dbos.dev/architecture)). That is too much infrastructure for a local tool, though its idea of checkpointing at stage boundaries and checking the code version on resume transfers directly. tmux, the approach claude-squad takes, suits interactive terminal agents rather than headless `claude -p` with structured output ([claude-squad tmux.go](https://raw.githubusercontent.com/smtg-ai/claude-squad/main/session/tmux/tmux.go)).

Five safeguards would close the holes, in order of value:

1. **Process identity.** Store `pid`, `pgid`, process start time and boot ID in the record, and require all of them to match before signalling a process or declaring it dead. Together, PID and start time are unique within a boot ([subc-os process_identity](https://docs.rs/subc-os/0.1.10/src/subc_os/process_identity.rs.html)).
2. **Heartbeat.** Have the supervisor write a heartbeat every 10 to 30 seconds. The server can then tell running, hung and "crashed with no final record" apart, and write a synthetic "supervisor lost" record for the last case. The lease needs an owner who acts when it expires. Hermes Agent's workers left claims stuck in `running` because a TTL alone fixed nothing ([hermes-agent#22926](https://github.com/NousResearch/hermes-agent/issues/22926)).
3. **Kill by process group, with the tree walk as a fallback.** Spawn the pipeline with `detached: true` so its PID is its PGID, then stop with SIGINT, SIGTERM, and finally SIGKILL on `-pgid`. A group kill reaches descendants that were reparented to PID 1, which the `ps` walk misses. Sending SIGINT first matters for Claude Code: SIGTERM leaves the current turn "unfinished and records no result", while SIGINT ends it cleanly ([Claude Code headless](https://code.claude.com/docs/en/headless)).
4. **Orphan reaping at server start.** Check identity, find members of a dead supervisor's process group that are still alive, and report or kill them.
5. **Stage checkpoints that record each agent's `session_id`**, so a resumed stage can continue with `claude -p --resume`.

macOS caps how far this can go. It has no child subreaper and no parent-death signal that survives exec, so orphans go to launchd, and cross-platform libraries rely on an identity check at the next start to reclaim them ([systemprompt-loader](https://docs.rs/systemprompt-loader/latest/systemprompt_loader/subprocess/index.html); [Go subreaper](https://pkg.go.dev/github.com/jamesits/machineproxy@v1.2.1/pkg/subreaper)). Tools that call `setsid` themselves also escape the process group. Only a Linux cgroup catches them. On Linux, launching the supervisor through `systemd-run --user --unit=sdlc-<slug> --collect` adds a kernel-level "kill everything this run started" ([systemd-run(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-run.html)). One caveat for Linux: if `ui` itself runs under a systemd unit with the default `KillMode=control-group`, stopping that unit kills the detached supervisors too, because `setsid` does not leave the cgroup. That was inferred and not tested. Separately, triage sessions should move onto the same detached-supervisor path or be explicitly reaped, and the palette should refuse `pipeline`.

## Tests collide on CPU first; Docker belongs on opt-in suites

Each run has its own git worktree, but its test processes share nearly everything else with every other run and with the user's shell. Suites run with the parent's full environment, minus one variable, with no per-run `TMPDIR`, `HOME`, port or database variable ([src/runners/run.ts](../../src/runners/run.ts)). By default `node_modules` is symlinked from the main checkout into every worktree, so an agent's `npm install` in one run changes the dependencies every other run is testing against ([src/config/settings.ts](../../src/config/settings.ts)). The only interference observed so far is CPU and process-start contention. This repo's own Vitest config caps workers at `min(4, cpus-1)`, because "with one worker per CPU they starve each other (and macOS's per-exec checks) and time out under load" ([vitest.config.ts](../../vitest.config.ts)). A known flaky triage test races a fixed 1,500 ms sleep against two HTTP calls. Fixed ports, shared databases through an inherited `DATABASE_URL`, and fixed `/tmp` paths are latent risks that will surface once a target project has integration tests.

Docker would isolate ports, `/tmp`, `HOME`, the environment, dependencies and services, but it costs a lot on macOS. In a 2025 benchmark of `npm install` on an M4 Pro, a bind mount took **9.5 s on Docker Desktop VirtioFS against 3.4 s native**, and 4.2 s on OrbStack. Bind-mounting the code and keeping `node_modules` in a named volume brought every runtime to 3.2 to 4.1 s ([Mainardi 2025](https://www.paolomainardi.com/posts/docker-performance-macos-2025/)). Container start-up on macOS Docker Desktop has been measured at about 1.5 s cold ([arXiv 2602.15214](https://www.arxiv.org/pdf/2602.15214)), and other measurements report much lower warm figures, so the real cost here needs measuring. Docker also cannot reuse the symlinked `node_modules`, because esbuild, rollup and fsevents ship darwin-arm64 binaries that must be reinstalled for Linux ([esbuild](https://esbuild.github.io/getting-started/)). And containers do not fix CPU contention on a Mac: every container shares one VM's fixed CPU and RAM, whose memory defaults to 50% of host RAM ([Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/)).

That points to three tiers. **Tier 0, on by default:** give each run its own `TMPDIR` and XDG directories, export `SDLC_RUN_ID`, an allocated `PORT`/`SDLC_PORT_BASE` and an `SDLC_DB_SUFFIX` (which test setup can combine with `JEST_WORKER_ID` to name per-worker databases, per [jest#2284](https://github.com/jestjs/jest/issues/2284)), use a per-worktree `node_modules` whenever the lockfile differs, and apply the CPU budget described in the next section. Overriding `HOME` should stay opt-in, because it breaks git identity, npm auth, Node version-manager discovery and agent login. **Tier 1, opt-in:** wrap tests in an OS sandbox. On Linux, bubblewrap or `unshare -n` gives each run a private network namespace, so fixed ports cannot collide. On macOS, Seatbelt (via `srt`) only filters connections and limits writes ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)), so it guards against damage but does not isolate ports. **Tier 2, opt-in per suite:** `isolation: "docker"` for integration suites that need services. Mount the worktree at the same absolute path, put `node_modules` in a volume per worktree, give each run its own network, and bring services up with a compose project per run or with Testcontainers' random host ports ([testcontainers-node#750](https://www.github.com/testcontainers/testcontainers-node/issues/750)). On macOS, recommend OrbStack. The wrapper belongs in the suite's `runCmd`, which already passes through `wrapCommand`. The pipeline, the integration gate and the agents (allowed `Bash(${runCmd}:*)`) would then all run tests the same isolated way. Agents themselves are better kept on the host inside their own sandboxes (Claude Code's Seatbelt/bubblewrap, Codex `workspace-write`) than containerised. Containers bring login friction, duplicated toolchains, and slower file reads on every agent Read and Grep ([Claude Code sandbox environments](https://code.claude.com/docs/en/sandbox-environments); [Codex sandboxing](https://learn.chatgpt.com/docs/sandboxing)).

## A shared test-slot budget beats OS priority tricks

Today the tool has one run cap, `DEFAULT_MAX_PARALLEL = 2`, and a start past it is refused with exit 3 rather than queued. It also has one test knob, `tests.maxWorkers`, which is off by default and reaches only Vitest and Jest ([src/runs/index.ts](../../src/runs/index.ts); [src/config/settings.ts](../../src/config/settings.ts)). With watch off, Vitest defaults to all available parallelism ([Vitest maxWorkers](https://vitest.dev/config/maxworkers)), and Jest defaults to cores minus one ([Jest CLI](https://jestjs.io/docs/cli)). So two runs gating at once on this 10-core M1 Pro start about 20 workers, before counting the agents' own test runs. Nothing sets priority, memory limits, or a budget shared across runs.

"Allocating more resources" here really means dividing a fixed machine fairly, and the OS levers are weaker than they look. **macOS has no cgroups.** Its background QoS and `taskpolicy -b` confine a process to the E-cores, only two on this machine ([Eclectic Light](https://eclecticlight.co/2025/05/09/what-is-quality-of-service-and-how-does-it-matter/)). They also throttle disk I/O, and network I/O on any socket opened afterwards, which would slow the agents' API calls (local `man setpriority`). An unprivileged process cannot raise its priority back once lowered. Plain `nice` on test spawns is safe but weak, and `taskpolicy -m <MiB>` is the only per-process memory cap that needs no root, though what it does at the limit is undocumented. **Linux is better served.** A transient `systemd-run --user --scope` per run with `CPUWeight`, `MemoryHigh` and `MemoryMax` gives proportional sharing that applies only under contention, plus a hard memory ceiling, and can be adjusted at runtime ([systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)). It does depend on the user manager having the cpu controller delegated, so probe for it and fall back to `nice`. On every platform, `NODE_OPTIONS=--max-old-space-size=<MiB>` set per test spawn caps each JS worker's heap ([Node CLI](https://nodejs.org/api/cli.html)). A runaway test then fails inside its own run instead of pushing the Mac into swap.

The more effective lever is the orchestrator, following how CI systems budget concurrency: fixed slot counts plus concurrency groups for heavy steps ([Buildkite concurrency](https://buildkite.com/docs/pipelines/controlling-concurrency); [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency); [Nx parallel](https://nx.dev/docs/kb/run-tasks-in-parallel)). Agent turns mostly wait on the network. Test gates are the CPU, memory and process-spawn hogs. So keep `maxParallel` as a cheap cap on whole runs and raise its default. Add a separate `maxHeavy` (1 or 2) for concurrent test gates, implemented as slot files under `<reg>/.heavy/` that are taken with exclusive create and freed when their holder is dead. When a slot is granted, set `--maxWorkers = max(1, floor((availableParallelism() − reserve) / gatesInUse))`, capped by the project's own setting. Before granting a slot, check load average and memory pressure (`kern.memorystatus_level` on macOS, PSI on Linux), and queue starts instead of refusing them. The budget formula and pressure thresholds are design proposals, not measured values, and need tuning. One compatibility note: `os.availableParallelism()` arrived only in Node 18.14 ([Node os](https://nodejs.org/api/os.html)), and the repo calls it without a fallback.

## Four full-suite runs per pipeline dominate the wall time

The pipeline's stages are serial by design, so the gains lie inside the gates, and the largest is repeated test work. A run started at Spec that goes green on the first Implement attempt executes these suite runs:

| Where | Run |
|---|---|
| Red tests gate | full suite, then a retry of the failing files (which always fail at this gate) |
| `red.json` | full suite again, in a temporary worktree at the red commit |
| Implement gate | target files, then full suite |
| Review gate | target files, then full suite, even if Review changed nothing |

Sources: [src/pipeline/stages.ts](../../src/pipeline/stages.ts), [src/pipeline/gates.ts](../../src/pipeline/gates.ts), [src/runners/run.ts](../../src/runners/run.ts). On a project like this one, whose suite takes 584 to 790 s ([docs/investigations/vitest-ontaskupdate-timeout.md](../../docs/investigations/vitest-ontaskupdate-timeout.md)), each avoided full run saves 10 to 13 minutes. The savings below come from reading the code and were not timed.

Five changes, ranked by return:

1. **Reuse the Red tests gate's result as `red.json`** whenever no non-test files were left uncommitted, and reconsider retrying failures at that gate. This saves one full run and one partial run per pipeline at little effort.
2. **Skip the Review gate's suite when the tree is unchanged since the last green gate.** `Git.sourceHash` already fingerprints the source ([src/pipeline/git.ts](../../src/pipeline/git.ts)). Generalise it into a Turborepo-style result cache keyed on tree hash, lockfile, suite config and runner version ([Turborepo caching](https://turborepo.dev/docs/crafting-your-repository/caching)). The same cache would also cover Test repair's repeated runs.
3. **Gate Implement attempts before the last on affected tests only,** using Vitest `--changed <sha>` and Jest `--findRelatedTests`/`--changedSince` ([Vitest affected tests](https://github.com/vitest-dev/vitest/blob/main/docs/guide/recipes/affected-tests.md); [Jest CLI](https://jestjs.io/docs/cli)). Keep the full suite for the deciding gate. Tests that read fixtures by path fall outside the import graph and would be missed, so the final full run must stay.
4. **Port the test runner from `spawnSync` to async `spawn` with the abort signal** ([src/runners/run.ts](../../src/runners/run.ts)). This lets Stop interrupt a suite, and it is the precondition for running multiple suites concurrently under the shared worker budget.
5. **Resume the agent session across Implement attempts** with `--resume <session_id>` instead of a cold `claude -p` that re-reads the spec, plan and source ([Claude Code headless](https://code.claude.com/docs/en/headless)). The prompt cache lasts 5 minutes by default ([prompt caching](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)), so after a long gate the resumed session saves exploration turns but not cache reads. That is one more reason to shorten the gates. Review and the Test repair audit should keep fresh sessions, because their independence is deliberate.

On the web pane, every git, `ps` and `gh` call is synchronous on the one server event loop, so a slow call freezes every tab and SSE stream. The run page polls a full `runView` every 2 s, and the drawer every 2.5 s. Each call re-runs `merge-base`, `diff` and `status`, and for finished runs it calls `gh pr view` synchronously with a 3-second timeout. Opening the Completed view calls `gh` once per task, one after another ([web/server/index.ts](../../web/server/index.ts); [src/runs/view.ts](../../src/runs/view.ts); [src/runs/completed.ts](../../src/runs/completed.ts); [src/pipeline/finalise.ts](../../src/pipeline/finalise.ts)). Make `gh` async with stale-while-revalidate caching, push run views over the shared SSE poller already planned in `docs/plans/dashboard-performance.md`, and extend that plan's context cache to every GET route. Smaller wins include cloning `node_modules` copy-on-write (`cp -c`) instead of running `npm ci` from scratch when Plan adds dependencies ([src/pipeline/deps.ts](../../src/pipeline/deps.ts); [Node 18 fs COPYFILE_FICLONE](https://nodejs.org/docs/latest-v18.x/api/fs.html)), and booting the runner once for all unclaimed files rather than once per file. A central daemon would not speed up the pipelines themselves. Its benefits (push events, a run queue, a shared budget) are available without one, through slot files, watchers and the planned poller.

## Conclusion

The question framed process isolation as missing, but the tool's real risk runs the other way. Its isolation works so well that a supervisor or pipeline killed alone leaves **invisible, unkillable orphans editing a worktree** that the registry calls stopped and that a new run may enter. The next increment is identity, heartbeats and process-group kills, not a new process architecture. On resources and performance, the same lesson applies: the scarce resource is the CPU during test gates, and both the contention and most of the wall time come from running the same suites too often and too broadly. A shared test-slot budget and a result cache address both at once. Docker, cgroups and daemons are worth adding later as opt-in tiers.

Three unknowns should be measured before committing to defaults. First, the split of a typical run's time between agent work and gate work: add per-stage `agentMs` and `gateMs` to `status.json`. Second, how the real Claude Code CLI behaves on SIGHUP and EPIPE: the experiments used `sleep` as a stand-in. Third, container start-up and Vitest-over-bind-mount timings on this Mac under OrbStack versus Docker Desktop.
